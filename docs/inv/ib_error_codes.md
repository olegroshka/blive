# INV-14 — IB Error Codes

## Purpose

Catalogue every IB error code blive's adapter has observed against IB Paper Gateway, with the typed-exception mapping the adapter applies and the operator action (when any). Authored at M2-IB.3b-ii close from observed-rejects on the wire-level probes; widens through M2-IB.4 (write-side rejects) and M5 (reconciliation drift).

This is **not** an exhaustive IB error catalogue — that lives in IB's TWS API docs (sourced above). It is the subset blive *handles*: maps to a typed exception, surfaces a useful message to the operator, and (where applicable) drives FSM transitions / reconciliation actions.

## Scope

**In:** error codes blive has observed and decided how to handle; adapter-side mapping (which `IBError` subclass / FSM transition); operator action.

**Out:** every IB error code in the TWS API docs (link in `sources`); broker / order-state semantics that aren't error-driven (those live in [INV-13](order_state_transitions.md)).

The order reaches ACCEPTED with `orderStatus.mktCapPrice` set to the cap level. If the market moves away from the cap during the order's lifetime, the order does not fill — visible to the broker only as a non-fill (the cap binds silently). Logged in `trade.log` with `errorCode=2161` and `status="ValidationError"` immediately before `status="Submitted"`. The post-acceptance disambiguation in `_on_order_status` (gated on `tracking.accepted_emitted`) correctly treats 2161 as informational rather than rejection — the FSM transitions remain SUBMITTED → ACCEPTED → CANCELED (engine-cancel on timeout) or → FILLED if the cap binds favourably. | **Empirically confirmed at M2-IB.6.2b/c (2026-05-06): no operator-side toolkit available in code bypasses the cap on UK retail accounts.** Tested across four wire runs against QQL3 on LSEETF: (1) raw MKT 10s wait — 0/5 fills, cap=38.5; (2) raw MKT 60s wait — 0/5 fills, cap=38.9, full 60s in Submitted state; (3) **ADAPTIVE_MKT (IB's recommended IBALGO Adaptive)** — 0/5 fills, cap=39.4, FSM trace differs (PreSubmitted → Submitted → ValidationError) but cap still binds; (4) **LMT @ $50** (single-shot probe; well above IB ref ~$39, within allowed-range envelope) — 0/1 fill, cap=39.4, IB literally cap-rounded the $50 LMT to $39.4 per the warning text *"to {cap} or a more aggressive price still within your specified limit price"*. Bypass requires either **MiFID II Professional Client classification** (per ADR-047 §"Alternatives Considered" item 2 — operator declined) or **substituting non-leveraged products on the affected venue**. Trigger correlates with **product volatility / leverage**: QQL3 (3× Nasdaq ETP, median 3.91% / max 11.74% daily range over last 60 bars) triggers consistently; IBTM (1× UCITS Treasury ETF, median 0.52% range) does not. Captured in OQ-031 (Phase 1 deployment under PMA-bound retail) for resolution before live cutover. The `OrderType.ADAPTIVE_MKT` infrastructure (added at M2-IB.6.2c) stays in the catalogue as useful tooling — it changes the FSM trace and may help fill quality on non-cap-bound venues / future strategies — but it is *not* a fix for the PMA-cap on UK retail leveraged ETPs. |

## Reason-extraction taxonomy (broker side)

Added at v0.6 (2026-05-04) after the M2-IB.6.2 probe surfaced that the v0.5 narrative ("`_rejected_reason_from_log_entry` handles both 201 reason strings identically") was wrong: the broker's reason-parsing was *empty-string* on the PRIIPs/KID variant.

ib_async surfaces IB error pushes through **two channels**:

| Channel | Carrier | Populated for |
|---|---|---|
| **Per-trade `trade.log`** | `TradeLogEntry` with `errorCode` + `message` set | error 200 (`No security definition`), error 10311 (direct-routing precaution), error 322 (dup orderId), warning 399 (held until next session open). Status transitions to `"Cancelled"` with the error log entry attached on the same wire-message tick. |
| **Global `ib.errorEvent`** | `(reqId, errorCode, errorString, contract)` | error 201 PRIIPs/KID variant, possibly other "broker-rejection-at-acceptance-layer" classes. Status transitions to `"Inactive"` with an *empty-message* `Inactive` log entry; the error text is **only** on the global channel. ib_async dispatches `statusEvent` *before* `errorEvent` for the same wire message. |

`IBBroker` subscribes to **both** channels at `connect()` (added at v0.6):

- The per-trade `statusEvent` handler (`_on_order_status`) handles the `Cancelled-with-errorCode-in-log` disambiguation path via `_last_error_log_entry` + `_rejected_reason_from_log_entry`. Wire-validated by codes 200 / 10311 / 399 / 322.
- The global `errorEvent` handler (`_on_ib_error`, added at v0.6) stashes `(errorCode, errorString)` keyed by `reqId` (= `orderId` for order-related errors; connection-level events with `reqId <= 0` are ignored).
- The `Inactive`-status branch in `_on_order_status` schedules a deferred async helper `_emit_rejected_via_inactive` that yields the event loop a few times before reading the trade-state and the stash — necessary because ib_async dispatches `statusEvent` before `errorEvent` for the same wire message, so a synchronous lookup at the moment the status handler fires reads an empty stash.

Reason-extraction chain for any `Inactive` rejection:

1. `_rejected_reason_from_trade(trade)` — read `trade.log[-1].message` then `whyHeld`. Returns the message text if either is populated, otherwise `None`.
2. `_reason_from_error_stash(orderId)` — look up the stash; format as `"ib:{code} {message}"` per the existing INV-13 §5 reason taxonomy (or `"ib:{code}"` if message is empty).
3. Fallback: literal `"rejected"` + `log.warning` so the breadcrumb is findable in retros if both channels turn up empty (would indicate an ib_async dispatch regression).

The Cancelled-with-errorCode-in-log path was *not* changed at v0.6 — it remains wire-validated and uses `_last_error_log_entry` + `_rejected_reason_from_log_entry` synchronously. Future codes that surface only on `errorEvent` (not in `trade.log`) will be picked up by the new stash automatically; v0.6 lifts the broker from "200/10311/322 only" to "any error reachable from either channel".

## Open Questions

None blocking. STABLE flip when M2-IB.4 has populated the §"Error catalogue" with the remaining order-side codes (322 dup orderId still on the forward list) — at that point the catalogue is no longer a stub against the §"Codes catalogued in KB-3 but not yet observed" forward list. Both the disambiguation path (code 10311 + 201) and the happy-path SUBMITTED → ACCEPTED → CANCELED (codes 202, 399) are now wire-validated for both AAPL/SMART and CAC.PA/SBF via the M2-IB.4a probes (2026-05-02).

**The IB Paper "Direct Routed Orders" restriction at error 10311 IS bypassable via API → Precautions** — but only when the **master bypass (item #1 "Bypass Order Precautions for API Orders")** is ticked, AND the more specific item #7 "Bypass Redirect Order warning for Stock API Orders" was also useful at validation time. Earlier session notes that called this a "hard restriction" were wrong: with the operator's bypass applied, CAC.PA on SBF reached ACCEPTED on the wire (held until next session open per warning 399). M2-IB.5 (Phase 1 strategy run on CAC.PA) is unblocked from the IB Gateway side. The probe-local `_SmartUsResolver` workaround in `scripts/probe_ib_submit.py` remains as a fallback when the bypass isn't applied (also good production guidance for US equities, where SMART routing is the IB-recommended pattern regardless).
